# 演習課題

易しい順に並べています。各課題で触るファイルと、終わったことを確かめる方法を書いています。どの課題も、**テストを先に書くか、テストを一緒に直す** ことを習慣にしてください。

---

## 初級

### 1. 料金プランを追加する

「ファミリー（`family`）」プランを追加する。

- 触るファイル: `backend/app/models.py`（`Plan`）、`frontend/src/pages/ApplyPage.vue`（`planOptions`）
- 確かめ方: 画面で選んで申込でき、`pytest` と `npm run typecheck` が通る
- 学べること: フロントとバックで型（選択肢）をそろえる必要がある。片方だけ直すとどうなるかも試す

### 2. 異体字を追加する

「嶋」を「島」の異体字として、対応表に追加する。

- 触るファイル: `backend/app/matching/normalize.py`、`backend/tests/test_matcher.py`
- 確かめ方: 「中嶋」と「中島」が一部一致（PARTIAL）になるテストを書いて通す

### 3. 結果画面の文言を変える

照合NG のとき、どの項目が違ったかを踏まえた案内を出す（例: 住所が違う場合は「マイナンバーカードの住所変更がお済みか確認してください」）。

- 触るファイル: `backend/app/routers/applications.py`、またはフロントの `ResultPage.vue`
- 考えること: 文言をバックとフロントのどちらで持つか。理由も説明できるようにする

## 中級

### 4. 住所の「番地の」に対応する

「1番地の2」と「1-2」を同じとみなす。

- 触るファイル: `backend/app/matching/normalize.py`、`backend/tests/test_normalize.py`
- 注意: 「の」を消すだけだと、「丸の内」のような地名まで壊れる。数字にはさまれた「の」だけを対象にし、テストで確かめる

### 5. 重複コールバックを観察する

```bash
cd backend
MOCK_VENDOR_DUPLICATE_CALLBACK=true uvicorn app.main:app --port 8000
```

- 画面から本人確認を1回行い、ログに `duplicate callback ignored` が出ることを確認する
- 学べること: 冪等性がないと何が起きるか。`ekyc_results.event_id` の UNIQUE 制約を外して試すと分かる（試したら戻す）

### 6. kintone の一時障害を観察する

```bash
MOCK_KINTONE_FAIL_FIRST_N=2 uvicorn app.main:app --port 8000
# 別のターミナルで
python -m batch.sync_to_kintone
```

- ログでリトライの様子を確認する。`MOCK_KINTONE_FAIL_FIRST_N=10` にすると、終了コードが 1 になることも確認する（`echo $?`）

### 7. PC からのアクセスで QR コードを出す

本人確認画面で、PC からのアクセスなら、スマホで開くための QR コードを表示する。

- 触るファイル: `frontend/src/pages/EkycPage.vue`
- ヒント: npm の QR コード生成ライブラリを使う。QR コードに載せる URL に、トークンをそのまま載せてよいか考える（画面を覗かれたら？有効期限は？）
- 学べること: 本番の設計で必ず出る「PC からスマホへの引き継ぎ」の設計論点

### 8. 照合ルールを設定で切り替える

「建物名の有無だけの違いは自動で OK にする」かどうかを、設定値（環境変数）で切り替えられるようにする。

- 触るファイル: `backend/app/config.py`、`backend/app/matching/matcher.py`、テスト
- 学べること: 業務ルールが決まっていない段階で、決定待ちにせず進める作り方

## 上級

### 9. 本人確認記録の保存期間を管理する

契約終了日を持たせ、「契約終了日から3年を過ぎた本人確認記録を削除する」バッチを作る。

- 考えること: 申込のまま契約に至らなかった場合はどう扱うか。誰に確認すべき論点か
- 成果物: 設計（[データ設計書](../design/04_データ設計書.md) への追記）、実装、テスト

### 10. コンテナにして Cloud Run に載せる

backend の Dockerfile を作り、API を Cloud Run（サービス）、バッチを Cloud Run Jobs で動かす。

- 考えること: SQLite のままでよいか（コンテナは再起動でファイルが消える）。秘密情報の渡し方
- 学べること: [クライゼルとGCPの基礎](05_クライゼルとGCPの基礎.md) の 2章

### 11. DB を PostgreSQL と SQLAlchemy に移す

- 触るファイル: `backend/app/db.py`、`backend/app/repository.py`
- 学べること: リポジトリ層に SQL を閉じ込めておくと、移行の影響範囲が小さいこと

## 設計の課題

### 12. 照合NG のあとの流れを設計する

照合NG になった申込者が、次に何ができるべきかを設計する。

- 例: 申込内容を修正して再照合する／カードの住所変更後にやり直す／店頭へ案内する
- 成果物: ビジネス側に説明するための1枚の資料（画面遷移、状態遷移、決めてほしいこと）
- 学べること: 要件を整理し、ビジネス側にロジックを説明する力が身につく

## AI ツールで進めるときのレビュー観点

Claude Code などに課題を任せた場合は、差分を次の観点で確認します。AI ツールを使った開発をふり返るときの材料にもなります。

| 観点 | 確認すること |
|---|---|
| 仕様 | 課題の意図どおりか。勝手に仕様を広げていないか |
| テスト | テストが追加・修正されているか。テストを弱めて通していないか |
| 境界値 | 空文字、長い文字列、全角、異体字、番地の途中一致など |
| セキュリティ | ログに個人情報を出していないか。署名検証やトークン確認を外していないか |
| 一貫性 | 既存の書き方（命名、例外処理、ログの形式）にそろっているか |
| 影響範囲 | フロントとバックの型、設計書の記述がずれていないか |

依頼のしかたの例:

> 「docs/catchup/06_演習課題.md の課題4に取り組んでください。まず backend/tests/test_normalize.py に失敗するテストを追加し、その後で実装してください。地名に含まれる『の』を壊さないことを確かめるテストも入れてください。」

**AI ツールに、業務のコード・データ・個人情報を入力してよいかは、必ず所属先やプロジェクトのルールを確認してください。**
